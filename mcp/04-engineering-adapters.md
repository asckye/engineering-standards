# 工程软件适配层

> **要点** 目标 API 只在适配层出现，它挂起或崩溃不能带倒服务。工具按版本的 API 证据注册，不靠推断。

进程模型不统一：独立 worker 进程和目标软件内的插件都可以。下面的规则约束的是行为。

## <a id="eng-isolation"></a>隔离与线程

- **MUST** `ENG-01` [两项目] 目标 API 只在适配层出现。除连接根对象和显式事务外，目标对象不跨请求持有，不跨进程传递，按名称或规范路径寻址。
  - 理由 · 跨请求持有目标对象会导致崩溃或误操作。
- **MUST** `ENG-02` [两项目] 服务进程和调用目标 API 的代码分开：独立 worker 进程，或目标软件内的插件加独立的服务进程。一方故障时另一方继续运行并报告。
  - 理由 · 目标组件崩溃不能带倒服务和审计。
- **MUST** `ENG-03` [两项目] 按厂商文档使用指定的线程与单元，调用前核对，不符时在调用前拒绝；不把原生调用挪到其他线程。
  - 理由 · 在错误的线程上调用会让目标软件崩溃或挂起。
- **MUST** `ENG-04` [一项目] 插件运行在目标软件进程内时：经统一的调度器在主线程上执行，调度有超时；委托内部捕获全部异常；有模态对话框时拒绝并报“忙”；主线程上不阻塞等待其他线程。
  - 理由 · 未捕获的异常会结束目标软件进程。
- **MUST** `ENG-05` [一项目] 对同一目标实例的调用串行，排队有上限：队列长度或等待时限，超过就拒绝。
  - 理由 · 大多数工程软件的 API 不能并发调用，无上限的排队会让工程师长时间无法工作。
- **SHOULD** `ENG-06` [一项目] 进程间协议有版本和握手，不匹配就拒绝，并提示怎么修复。需要防文件被替换时，握手核对文件哈希和一次性 nonce。

## <a id="eng-faults"></a>故障与超时

- **MUST** `ENG-07` [两项目] 适配层超时、退出或回复损坏时，不自动重放写入。适配层能确认结果就按确认结果报告，否则按结果未知处理（[`WS-23`](03-write-safety.md#ws-unknown)）。
  - 理由 · 故障后的状态不可信，继续调用会扩大损坏。
- **MUST** `ENG-08` [一项目] 每个跨边界调用有超时，按操作类别设预算（普通调用、首次连接、长操作），预算集中定义，可经配置覆盖。
  - 理由 · 没有超时的调用会让会话永久挂起。
- **SHOULD** `ENG-09` [两项目] 断开或退出时不隐式改变目标状态（保存、关闭、复位），需要时作为显式操作提供。
- **SHOULD** `ENG-10` [两项目] 有多个目标实例时不自动选择，由调用方或人明确指定；需要独占时用租约或等价机制，不靠结束其他进程。
- **SHOULD** `ENG-20` [一项目] 每个目标 API 调用前先落盘一行调用记录，崩溃后能知道最后发出的调用。

## <a id="eng-versions"></a>版本与注册

- **MUST** `ENG-11` [两项目] 工具只在 API 支持的目标版本上注册，至少一个动作有证据才注册。一份构建要支持多个版本、启动时还不知道版本时，可以全部注册，但在调用目标前拒绝不支持的动作。拒绝用明确的错误码，新服务用 `UNSUPPORTED_CAPABILITY`。
  - 理由 · 模型会调用该版本上不存在的能力。
- **SHOULD** `ENG-12` [一项目] “功能 × 目标版本”的支持关系只在一处声明，注册、发现、文档、示例和测试共用；各版本数量随 API 支持而定，不为一致而拉平，由生成目录给出，不手写。
- **MUST** `ENG-13` [两项目] 适配层按声明支持的版本编译：各版本 API 不兼容时分别按精确 SDK 编译；厂商保证二进制兼容时可以一份构建，并写明依据。构建核对引用的版本，不符就失败。厂商程序集不提交、不分发，除非许可证明确允许。
  - 理由 · 静默回退到其他版本会产生难以复现的缺陷，分发还可能违反许可。

## <a id="eng-behavior"></a>写入与厂商行为

- **MUST** `ENG-14` [一项目] 目标对某类操作提供事务或撤销时，这类写入每次放在一个事务内，合并为一个可撤销步骤并标明来源（如 `AI: <工具名>`）；读回校验通过才提交，其余路径回滚。目标不能回滚的操作写明，失败时按实际情况报告 `partial` 或 `rolled_back`，确实无法确定时才按结果未知处理。
  - 理由 · 半途失败会留下损坏的工程。
- **MUST** `ENG-15` [一项目] 写入、线程、回滚和崩溃相关的目标行为都有出处：厂商文档、SDK 元数据或实机验证记录的编号。这些记录写在 API 笔记中，含版本和验证日期，代码注释引用编号。
  - 理由 · 凭记忆或推断写的厂商行为是最常见的实机缺陷。
- **MUST** `ENG-16` [一项目] 用禁用 API 列表拦住“看似读取、实际写入”、占用许可或已知会使目标软件崩溃的成员。确需使用时就地抑制并写明原因。
  - 理由 · 看似读取的成员可能写入工程或占用许可。
- **SHOULD** `ENG-17` [两项目] 自动化代码不弹出界面（审批除外），能用静默模式时用静默模式；附着到用户打开的实例时不改变它的界面模式。目标弹确认框时选安全的一项并记录。检查许可时不占用许可。
- **SHOULD** `ENG-18` [部分实现] 操作前后收集目标软件的系统消息差异，把相关消息随结果返回。
- **SHOULD** `ENG-19` [两项目] 提供只读的自检命令，报告目标连接、许可、配置来源和环境问题，可输出 JSON。

## <a id="eng-structure"></a>代码结构

注释、命名、函数和文件规模按[通用规范第 3、4 节](../general/04-quality.md)。下面只写 MCP 服务特有的结构。

- **SHOULD** `ENG-21` [部分实现] 工具入口要薄：工具方法只做参数绑定和结果呈现，业务逻辑放在下层。
- **SHOULD** `ENG-22` [一项目] 写工具共用一条流水线：规划、审批、复核、执行和审计由共享代码完成，工具只提供规划和执行两步，新工具不会漏掉审批。
- **SHOULD** `ENG-23` [部分实现] 工具的名称、安全级别、注解和支持版本在一张登记表中声明，注册、文档和测试都读它。
- **SHOULD** `ENG-24` [部分实现] 版本差异只进适配层，工具层不写版本判断。
- **SHOULD** `ENG-25` [一项目] 文件按资源或领域拆分；新增一个工具要改哪些地方有清单，并由检查发现漏改。

## <a id="eng-checklist"></a>新增目标版本清单

- [ ] 取得该版本的 SDK 与文档，放在本机，不入库。
- [ ] 在版本登记表中加一行，并声明差异。
- [ ] 按 `ENG-13` 编译适配器；构建核对版本。
- [ ] 逐个功能核对 API 证据，生成目录和数量；不支持的动作返回明确的错误码。
- [ ] 示例按该版本 schema 生成；离线检查通过。
- [ ] 实机核对清单加入该版本；台账先标 `NOT RUN`，验证后更新；支持矩阵与发布说明同步。
