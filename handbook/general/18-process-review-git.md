# <a id="review"></a>18 开发流程、评审与 Git

> **要点** 需求先写验收标准，非平凡改动先有一页设计；小改动、快评审、短分支。

## <a id="review-flow"></a>18.1 生命周期

开发生命周期：1 问题或想法 → 2 需求与验收标准 → 3 设计评审 [M+] → 4 任务拆分 → 5 实现 → 6 评审 → 7 合并门 → 8 发布 → 9 反馈与缺陷登记

| 阶段 | 产出 | 负责 |
|---|---|---|
| 问题或想法 | 一句话问题陈述，登记在问题跟踪或计划中 | 维护者 |
| 需求与验收标准 | 需求说明（18.2） | 维护者或主导代理起草，维护者确认 |
| 设计评审 | 一页设计说明；需要时 ADR（只对 L2 及以上的改动） | 主导代理起草，维护者批准 |
| 任务拆分 | 可独立合并的任务说明（模板 T.4） | 主导代理 |
| 实现 | 代码、测试、生成文件、文档 | 实现者（人或实现代理） |
| 评审 | 评审意见与结论（18.5） | 评审者（人或主导代理） |
| 合并门 | 变基后的通过记录，合并到主干 | 评审者 |
| 发布 | 版本、发布说明（含“未验证”清单）、资产 | 维护者确认，主导代理执行 |
| 反馈与缺陷登记 | 分级的缺陷与测试反馈，回到第一步 | 维护者分级，主导代理诊断 |

## <a id="review-req"></a>18.2 需求与验收标准

- **SHOULD** `REQ-01` 开始工作前，每个功能写明：问题、用户、范围、不做什么，以及可测试的验收标准（Given/When/Then 或检查清单）。S 级项目可以只写问题和验收标准。
- **SHOULD** `REQ-02` 每条验收标准对应至少一个测试或一条实机核对项；做不到自动化时写明核对方法。

```markdown
# 需求：<功能名>
问题      谁在什么情况下遇到什么困难
用户      <角色>
范围      要做的
不做      明确排除的
验收标准
- Given <前提> When <操作> Then <可观察的结果>
- Given 输入超出范围 When 提交 Then 拒绝且目标未改变
```

## <a id="review-rfc"></a>18.3 变更级别与设计说明

| 级别 | 典型改动 | 需要的产物 |
|---|---|---|
| L0 | 笔误、注释、文档措辞 | 无 |
| L1 | 不改契约的修复、重构、补测试 | 任务说明 |
| L2 | 新功能、契约变化、新依赖、新数据格式、跨信任边界的功能 | 任务说明 + 一页设计说明 [M+] |
| L3 | 进程或部署结构、安全或设备安全边界、发布门禁、外部基线 | 设计说明 + ADR |

- **MUST** `REV-01` 每次合并前有评审（人或主导代理），评审者在变基后的提交上通过合并门；失败先定位原因再退回，不反复重跑。
  - 理由 · 未经评审和合并门的改动是回归的主要来源。
- **SHOULD** `REV-02` [M+] L2 及以上的改动在写代码前有一页设计说明，经维护者批准；其中长期有效的决定转写为 ADR。L0、L1 不写。

设计说明用模板 [T.3](../appendix/t-templates.md#tpl-rfc)。

## <a id="review-git"></a>18.4 Git

- **SHOULD** `GIT-01` 只有一条长期分支（主干）。任务分支短命，评审并通过合并门后变基到主干，快进或压缩合并，合并后删除。
- **SHOULD** `GIT-02` 有依赖的分支按依赖顺序逐个合并，每个都重新变基并过合并门；变基后重新生成生成文件，不手工合并它们。
- **MUST** `GIT-03` 用明确的路径 `git add <path>`，不用 `git add -A` 或 `git add .`。
  - 理由 · 防止把无关文件、密钥或构建产物一起提交。
- **MUST** `GIT-04` 提交信息用英文祈使句，标题不超过 72 字符，正文写原因；不加 AI 署名（`Co-Authored-By` AI、“Generated with”）。
  - 理由 · 历史可读、可检索；不混入不实的署名。
- **SHOULD** `GIT-05` 采用 Conventional Commits，破坏性变化加 `!`；每个仓库选定一种格式并写进代理说明。
- **SHOULD** `GIT-06` 一次改动只做一件事：生产代码加文档目标 200 行以内，超过 400 行拆分（测试、生成文件、快照不计）。
- **MUST NOT** `GIT-07` 提交二进制、厂商 SDK、用户项目、密钥、本机绝对路径和设计交接草稿。
  - 理由 · 这些内容一旦进入历史就很难清除。

## <a id="review-code"></a>18.5 代码评审

**目的**：在合并前发现缺陷，让下一个读代码的人（或下一个代理会话）能读懂，并让团队了解改动。评审不是风格之争，格式交给工具。

### 作者：请求评审前

- [ ] 改动只做一件事，规模在 GIT-06 以内；重构与行为变化分开。
- [ ] 本机构建通过，零新增警告，受影响的测试和合并门已运行。
- [ ] 自己读过一遍差异：没有调试代码、注释掉的代码、无关文件和本机路径。
- [ ] 说明写清：为什么改、怎么验证的、风险与回退办法、契约或数据格式的变化。
- [ ] 修复带修改前失败的测试；新功能有主要行为测试。
- [ ] 文档、CHANGELOG、注释已同步。

### 评审者：逐项检查

| 方面 | 问自己 |
|---|---|
| 正确性 | 主要路径和边界情况对吗？并发、取消、超时下呢？ |
| 设计与简单 | 该不该做？放在这里对吗？有没有更简单的做法？是否用了已有的扩展点和共享组件？ |
| 可读性与命名 | 不看说明能读懂吗？名称说的是“是什么”吗？ |
| 测试 | 代码出错时测试会失败吗？测试快、稳、独立吗？ |
| 错误处理 | 只在边界校验？错误明确、不吞异常？写入后的失败按“结果未知”处理？ |
| 安全 | 输入、路径、子进程、密钥、去敏、确认是否符合第 6 节？ |
| 性能 | 热路径上有没有多余的调用、分配或 IO？有计时证据吗？ |
| 一致 | 与项目已有的名称、结构、错误码一致吗？ |
| 文档与注释 | 注释说明原因吗？公开 API 有文档注释吗？有没有过期注释？ |

- **SHOULD** `REV-03` 评审意见标严重程度：**必须修改**（阻止合并）、**建议**（作者决定，不采纳时回复理由）、**Nit**（不阻止）。
- **SHOULD** `REV-04` [M+] 一个工作日内给出首次评审；作者逐条回复；复审只看改过的部分。
- **MUST** `REV-05` 以下任一项阻止合并：MUST 违规且无 ADR；新增分析器警告；检查被删除或放宽且未获批准；生成文件与生成器输出不一致；修复缺少回归测试；契约变化没有说明；含密钥或客户数据；未解决的“必须修改”意见。
  - 理由 · 明确的阻止条件避免评审各凭感觉。
- **SHOULD** `REV-06` 分歧按本规范和项目标准裁决；规范没有覆盖时由维护者决定，长期有效的结论写 ADR。同一点来回超过两轮就上交维护者。
- **MUST** `REV-07` AI 生成的代码用同样的标准评审，另外核对：没有推测性抽象和防御性膨胀（1.4）；没有没人要的配置项和测不到的状态测试；调用的 API 确实存在于对应版本的文档中；没有任务范围外的改动；没有放宽任何检查。
  - 理由 · AI 代码最容易带入推测性代码和臆造的 API。
