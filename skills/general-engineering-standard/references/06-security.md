# <a id="security"></a>6 安全

> **要点** 威胁集中在审批绕过、路径穿越、XXE、命令注入、本机认证、密钥泄露和提示注入。安全流程按等级取舍。

## <a id="security-scope"></a>6.1 范围与信任边界

- **SHOULD** `SEC-01` [M+] 威胁模型文档：资产、信任边界、STRIDE 威胁、措施及其测试、已知缺口，并写明前提与范围外的情况（例如“同一操作系统用户”是信任边界）。

## <a id="security-approval"></a>6.2 确认与审批不可绕过

- **MUST** `SEC-03` 需要人确认的操作，确认只来自人独立操作的界面（独立的审批窗口、目标软件内的对话框、操作员终端）；调用方的参数、元数据、批处理或客户端自己显示的表单都不能代替。
  - 理由 · 客户端能自己批准写入就等于没有审批。
- **MUST** `SEC-04` 确认请求号由服务端生成；决定绑定请求号、计划指纹和去敏后的参数摘要，只能使用一次；迟到、重复、不匹配或格式错误的决定一律按拒绝处理。
  - 理由 · 防止伪造、重放或张冠李戴的审批决定。
- **MUST** `SEC-05` 确认开关、可写范围等安全配置只能由人在配置文件或“仅人可改”的设置页修改；没有接口或工具能修改它们，也不能写这些文件（包括经短文件名、链接或文件 ID 的写法）。
  - 理由 · 防止自动化或 AI 关掉自己的保护。
- **MUST** `SEC-06` 确认关闭时，每个执行结果带“确认已关闭”的警告，有界面时持续显示该状态，开关变化写入审计。
  - 理由 · 确认关闭后写入没有人看，用户和模型都要知道这一点，事后也要查得到。

## <a id="security-path"></a>6.3 路径穿越与压缩包

- **MUST** `SEC-07` 外部给出的路径只接受固定根目录之下的相对路径：拒绝绝对路径、UNC、驱动器号、`.`、`..`、空段、控制字符、Windows 保留字符和保留设备名（`CON`、`NUL`…）；按规范化后的完整路径判断。
  - 理由 · 防止写到预期目录之外。
- **MUST** `SEC-08` 根目录之下的每一级都不能是符号链接、联接点或其他重解析点；写出后再列出目录，确认文件都在根目录内。
  - 理由 · 链接能把写入带到根目录之外，绕过 `SEC-07`。
- **MUST** `SEC-09` 导出和输出不覆盖用户已有的文件，除非调用显式允许且经确认（人在命令行上显式传入的覆盖参数算确认）；默认写入每次新建的空目录。
  - 理由 · 静默覆盖会丢失用户的文件。
- **MUST** `SEC-10` 压缩包在内存或新建的临时目录中读取：条目名按 SEC-07 校验，名称忽略大小写后唯一，拒绝链接条目；文件数、单文件大小、总大小、压缩比都有上限；不执行包内任何代码。
  - 理由 · 防止压缩炸弹和经压缩包的路径穿越。

## <a id="security-xxe"></a>6.4 XXE 与解析器

规则见 [`CODE-07`](03-code.md#code)。

## <a id="security-cmd"></a>6.5 命令注入

- **MUST** `SEC-12` 启动子进程只用参数列表或 stdin 传参，不经 shell，可执行文件和工作目录用绝对路径；限制超时和输出大小。各语言的做法见语言附录。
  - 理由 · 防止命令注入。
- **MUST** `SEC-13` 模型、外部请求或项目数据能触发外部命令、脚本或宏时，只执行随产品发布的白名单条目；参数逐个校验类型、枚举、范围、长度和字符集，拒绝引号和控制字符；没有工具、配置或数据文件能增改白名单。
  - 理由 · 否则模型或注入的内容可以执行任意操作。

## 6.6 本机管道与 HTTP

在用户或现场机器上运行的软件按[本机运行的软件](../../desktop-app-standard/references/local-software.md#security-ipc)。

## <a id="security-secrets"></a>6.7 密钥与凭据

- **MUST** `SEC-19` 密钥和凭据只存在受保护的存储中（本机软件用操作系统的受保护存储，如 Windows 的 DPAPI（当前用户范围）或凭据管理器、macOS 的 Keychain、Linux 的 Secret Service；服务端用密钥管理服务），不写入明文配置、命令行参数（会进入进程列表）或日志。
  - 理由 · 明文密钥会经配置、进程列表或日志泄露。
- **MUST** `SEC-20` 去敏规则统一一处实现：键名含 password、passwd、secret、token、credential、authorization，或以 key 结尾（明确的白名单除外）的值替换为固定占位符；自由文本中的 Bearer/Basic 令牌、`name=value` 形式的密钥、URL 用户信息、PEM 私钥清除。审批摘要、哈希、审计和日志都在去敏后计算。
  - 理由 · 防止凭据进入日志、摘要和响应。
- **SHOULD** `SEC-21` 新增带凭据的参数时，命名符合 SEC-20 的规则，并加测试证明值不进入确认摘要、审计、日志和响应。
- **MUST NOT** `SEC-22` 在仓库、文档、夹具、截图、Issue 中出现真实凭据、机器地址、客户项目或许可证信息。
  - 理由 · 提交过的密钥只能轮换，无法真正撤回。

## <a id="security-injection"></a>6.8 经项目数据的提示注入

- **MUST** `SEC-23` 来自用户项目或设备的自由文本（注释、属性值、标签名、导入文件内容）只作为数据返回，放在数据字段中，不拼进给模型的说明或摘要。
  - 理由 · 防止项目数据中的文字被模型当成指令执行。
- **MUST** `SEC-24` 这类文本交给模型或显示在审批界面前，剥除控制字符（保留换行和制表符）、双向文本控制符（U+202A–202E、U+2066–2069）和 Unicode 标签字符（U+E0000–E007F），超长时截断并注明原始长度；写回目标时用原文。
  - 理由 · 这些字符能伪造界面文字或隐藏内容，诱导人或模型。

## <a id="security-privilege"></a>6.9 最小权限

- **SHOULD** `SEC-27` CI 工作流令牌默认只读（`contents: read`），需要写权限的作业单独授予。

## <a id="security-sdl"></a>6.10 安全开发流程（SDL-lite）

- **SHOULD** `SEC-28` [M+] 威胁建模（只对跨越信任边界的功能）：新功能或新接口（新端点、新管道、新文件入口、新设备写入路径）在设计说明（[18.3](18-process-review-git.md#review-rfc)）中附一段简短威胁模型：画出信任边界，对每个边界按 STRIDE 列出威胁和措施；更新项目的威胁模型文档。
- **SHOULD** `SEC-29` 安全静态分析：启用语言的安全规则（见语言附录）为警告；新增违规阻止合并。
- **SHOULD** `SEC-30` [M+] 依赖漏洞扫描：每次合并和每周运行语言的扫描工具（见语言附录）；高危漏洞阻止发布。更新政策：高危 7 天内升级或给出缓解，中危下一个次版本处理，其余随常规更新。
- **SHOULD** `SEC-31` 密钥扫描：仓库启用密钥扫描（托管平台的 secret scanning 或提交前钩子）；发现泄露立即轮换，再从历史中清除。
- **SHOULD** `SEC-32` [M+] 发布前安全复核：对照威胁模型核对本版新增的边界和措施、去敏测试、依赖扫描结果；结论写入发布记录。
- **SHOULD** `SEC-33` [L] 或网络暴露：网络暴露模式（HTTP 等）在首次发布和每次改动认证、绑定或路由时做滥用测试：无密钥、错误密钥、暴力尝试、错误 Origin/Host、超大请求、畸形帧、跨会话访问句柄。
- **SHOULD** `SEC-34` [M+] 漏洞受理：仓库有 `SECURITY.md`（报告渠道、受理范围、响应时限）；收到报告 3 个工作日内确认并分级，高危 30 天内修复或发布缓解，修复后发布安全公告并在 CHANGELOG 中注明；事件处理按 [13.1](13-defects.md#bugs-triage) 的 S1 流程。

## <a id="security-crypto"></a>6.12 密码学

算法和参数会过时。这里写的是下限，具体选择以最新的 NIST 和 OWASP 指南为准（[参考资料](appendix/references.md#refs)）。

- **MUST** `SEC-35` 不自己设计或实现密码算法和协议，用平台或成熟库提供的实现和它的安全默认值。用标准构件（SHA-256、HMAC）组合的完整性记录不算，写明并评审。
  - 理由 · 自己写的密码代码几乎总有漏洞，而且测试发现不了。
- **MUST** `SEC-36` 安全用途不用已淘汰的算法：MD5、SHA-1、DES、3DES、RC4、ECB 模式。对称加密用带认证的方式（如 AES-GCM、AES-CCM、ChaCha20-Poly1305，或先加密后 MAC），同一密钥下 nonce 不重复。哈希用 SHA-256 及以上。签名用 RSA 2048 位及以上、ECDSA P-256 及以上或 Ed25519；密钥协商用 ECDH P-256 及以上或 X25519；RSA 加密用 OAEP。操作系统提供的数据保护（DPAPI、Keychain、全盘加密）按平台默认。校验非安全内容（如缓存键）的哈希不在此列，但要能看出用途。目标设备或协议只支持旧算法时，写进威胁模型作为剩余风险（没有威胁模型时写入 README）。
  - 理由 · 这些算法已经能被攻破，不带认证的加密还能被篡改。
- **MUST** `SEC-37` 用户登录本产品的口令只存加盐的慢哈希（优先 Argon2id，其次 scrypt；bcrypt 只用于已有系统，PBKDF2 用于要求 FIPS 的场合；参数按 OWASP 当前建议），不存明文，也不用可逆加密。代为登录其他系统的凭据按 `SEC-19`。
  - 理由 · 数据库泄露时，普通哈希很快就能被破解，而且用户常在别处用同一个口令。
- **MUST** `SEC-38` 跨网络传输凭据、个人数据和客户数据时用 TLS 1.2 及以上（能用 1.3 时优先）或同等的安全通道（SSH、VPN、OPC UA SignAndEncrypt）；校验证书和主机名，或按人配置的信任列表、证书指纹校验；发布版没有跳过校验的开关。下列情况除外，作为剩余风险写入威胁模型（没有威胁模型时写入 README）：本机回环；局域网或私有网络上的本机软件 HTTP（`SEC-15`、`PRO-23`）；本身没有加密的设备协议（如 Modbus TCP），只在隔离网段使用；我们运行的服务在同一私有网络内部的流量。
  - 理由 · 明文或不校验证书时，同一网络上的人能读到或改掉内容。
- **MUST** `SEC-39` 令牌、会话标识、随机生成的 nonce 和密钥用密码学安全的随机数生成，不用普通随机数；比较密钥、令牌和签名用恒定时间比较（时间不随内容变化，如 `CryptographicOperations.FixedTimeEquals`、`hmac.compare_digest`、`crypto.timingSafeEqual`），不用 `==`。
  - 理由 · 普通随机数可以被预测，逐字节比较可以被计时攻击。
- **SHOULD** `SEC-40` 加密数据的明文密钥不和密文放在同一存储；信封加密时，被加密的数据密钥可以和密文放在一起，操作系统保护的存储算作单独存储。硬编码按 `SEC-19`。
- **MUST** `SEC-41` [M+] 我们运行的系统、我们保管的备份，以及产品自动发到本机之外的备份，其中的个人数据和客户数据加密存储；依赖磁盘或数据库加密时写明。恢复所需的密钥和备份分开保管，并纳入 `OPS-13` 的恢复演练。用户自己发起的导出不强制加密，用户文档写明其中可能含敏感数据。
  - 理由 · 磁盘或备份丢失时，数据不能跟着泄露；密钥丢了，加密的备份也就没了。
- **SHOULD** `SEC-42` [M+] 算法和参数集中在一处；加密数据和哈希带算法标识，换算法时能迁移旧数据。支持期超过 2030 年、或数据要保密到 2030 年以后的产品，写明后量子迁移计划（NIST IR 8547）。

## <a id="security-accounts"></a>6.13 仓库和发布账号

- **MUST** `SEC-43` [M+] 代码托管、包源、应用商店和更新通道的账号开启多因素认证，恢复码离线保存。发布令牌只给发布流程，权限最小；代理（`AI-20`）和不可信来源触发的 CI 作业（如 fork 的 PR）拿不到。只有一个人持有时，写明这个人不在时谁能恢复账号和签名密钥（`OPS-01`）。
  - 理由 · 账号或令牌被盗时，攻击者可以发布恶意版本，用户会直接装上；唯一的持有人联系不上时，修复也发不出去。

## <a id="security-regulation"></a>6.14 产品安全法规

- **MUST** `SEC-44` [M+] 产品面向欧盟用户销售或公开下载时，按[标准对照](appendix/standards-mapping.md#mapping-cra)的步骤写 ADR：Cyber Resilience Act（EU 2024/2847）是否适用，角色（制造商、进口商、经销商、开源软件管理者（open-source software steward），或都不是），产品类别；同时列出其他适用的产品法规。适用时按法规履行，不能用 ADR 免除。制造商的上报义务已经生效，也覆盖已上市的产品：被实际利用的漏洞和严重事件 24 小时内预警、72 小时内通报，之后提交最终报告，并通知受影响的用户；事先在 ENISA 单一报告平台注册。
  - 理由 · 第 14 条从 2026-09-11 起适用；其余要求从 2027-12-11 起适用于之后投放市场或实质修改的产品。违反可能被罚款（第 64 条；小微企业错过 24 小时预警不罚，开源软件管理者不罚），或被要求整改、撤回、召回（第 54 条）。
