# 协议层

> **要点** 协议细节交给官方 SDK。服务不依赖协议会话；流断开后客户端会用新请求号重发，所以重发不能绕过审批。

本层按 MCP 2026-07-28 编写。MCP 改版时主要修改本层。

## <a id="pro-revision"></a>修订与 SDK

- **SHOULD** `PRO-01` 写明支持的 MCP 修订，写入发布说明或用户文档；升级修订写 ADR。
- **MUST** `PRO-02` 服务支持 MCP 2026-07-28，可以同时支持旧修订。
  - 理由 · 本层的规则都以这个修订为前提；只支持旧修订的服务无法按本规范判断是否合规。
- **SHOULD** `PRO-24` 官方 SDK 有稳定版本时用稳定版本；还没有时可以用预览版本，锁定版本并写明。
- **MUST** `PRO-03` [规范] `server/discover`、`resultType`、`ttlMs`、`cacheScope` 和请求元数据校验由 SDK 产出，或按规范实现，不手写半套协议。
  - 理由 · 这些字段是 2026-07-28 的必需项，缺了客户端无法协商或缓存。
- **SHOULD NOT** `PRO-04` [规范] 依赖已弃用的 Roots、Sampling、Logging 功能。目录用工具参数传，日志写 stderr 或文件。

## <a id="pro-errors"></a>两条错误通道

- **MUST** `PRO-05` [规范] 只有协议层问题（未知工具、请求格式错误、服务器错误）用 JSON-RPC 错误。参数错误、拒绝、执行失败、部分完成和结果未知都作为 `isError: true` 的工具结果返回。写入派发之后的任何失败都走工具结果并带 `execution`，不走 JSON-RPC 错误。
  - 理由 · 模型读不到错误原因就会盲目重试。

## <a id="pro-list"></a>工具列表

- **MUST** `PRO-06` [规范] `tools/list` 不随连接变化，也不因其他请求的副作用变化。本规范进一步要求工具集由部署配置（目标版本、档位）决定，不随调用过程增减。
  - 理由 · 协议已没有连接级状态，随调用变化的工具列表会让客户端缓存失效或用错工具。
- **SHOULD** `PRO-07` [规范] `tools/list` 的顺序固定，并有测试核对，便于客户端缓存和模型提示词缓存。

## <a id="pro-state"></a>跨调用状态

- **MUST NOT** `PRO-08` [规范] 把连接或进程当作会话来关联两次调用。需要关联时按 `PRO-09`。
  - 理由 · 2026-07-28 没有协议级会话，规范明确说连接或进程不代表会话连续性；客户端可能在同一连接上交错发送不相关的请求。
- **MUST** `PRO-09` [规范] 跨调用状态（绑定的目标、计划、任务）用显式标识引用，调用方每次传入。标识由服务生成，不透明、随机，有期限，有效期写在创建工具的描述或结果中；过期时返回可恢复的工具错误。
  - 理由 · 这是 2026-07-28 的要求；工程软件的连接和项目绑定天然有状态，隐式状态会让模型操作到错误的目标。
- **MAY** `PRO-10` 部署时固定的内容（一个服务实例对应的目标版本或目标实例、工具档位）放在进程配置中，不算跨调用状态，在文档中写明。运行中切换目标不在此列，按 `PRO-09`。
- **MUST NOT** `PRO-11` [规范] 把持有句柄当作通过认证。
  - 理由 · 句柄可能被猜到或泄露。

## <a id="pro-retry"></a>断流、重发与取消

- **MUST** `PRO-12` 客户端重发不能绕过审批。流断开后客户端必须用新请求号重发，stdio 进程退出后客户端也可以重启并重试，所以写工具不靠 JSON-RPC 请求号判重：重发要么被一次性计划或写入编号识别而不再执行，要么重新走规划和审批。识别出重发时返回原次写入的结果，`execution` 取原次的值；原次还在执行时，等它结束或按 `WS-21` 查询，不返回 `not_started`。重新规划排在原次结束之后，预览看到的是原次之后的状态。
  - 理由 · 否则客户端按规范重发，就会在无人确认的情况下把同一修改做两次。流断开后，原次的结果只能经重发带回，回 `not_started` 会让模型以为目标没变。
- **SHOULD** `PRO-22` 一次性项目上免审批的写入可能因重发做两次，工具描述要提示这一点。
- **MUST** `PRO-13` [规范] Streamable HTTP 上把客户端断开当作取消，stdio 上处理 `notifications/cancelled`。写入已派发到目标时按 [`WS-25`](03-write-safety.md#ws-unknown) 处理。取消后不再为这个请求发送任何消息，结果只进审计。
  - 理由 · 断开和取消在 HTTP 上是同一个信号，不能当作写入失败。

## <a id="pro-long"></a>长操作

- **SHOULD** `PRO-14` 收到进度令牌时，在排队、等待审批和长操作期间按固定间隔发送单调递增的进度。进度不代表成功。
- **MAY** `PRO-15` 预计超过约 30 秒的操作，在客户端声明支持 `io.modelcontextprotocol/tasks` 时可以返回任务。任务先持久化再返回；客户端未声明时保持同步并发送进度。
- **MUST** `PRO-16` [规范] 如果使用多轮请求的 `requestState`，把它当作攻击者可控的输入：影响授权或业务逻辑时做完整性保护（规范的 MUST），并绑定请求、期限和调用方（规范的 SHOULD）。需要一次性语义时由服务端保证。
  - 理由 · `requestState` 经过客户端，可能被篡改或重放。

## <a id="pro-transport"></a>传输

- **SHOULD** `PRO-17` 本机使用优先 stdio。只有目标在虚拟机或另一台机器上时才用 HTTP。
- **MUST** `PRO-18` [规范] HTTP 请求的 `Origin` 存在且不在允许列表中时回 403（规范的 MUST），允许列表默认不超过本端点。本规范进一步要求校验 `Host`。没有 `Origin` 的请求不因此拒绝，靠 `PRO-19` 认证。
  - 理由 · 防止网页经 DNS 重绑定访问本机服务。
- **MUST** `PRO-23` 本机只绑定 `127.0.0.1`，局域网只绑定人选择的具体地址，不监听所有接口。明文 HTTP 只在私有网络中使用，作为剩余风险写入威胁模型（没有威胁模型时写入 README）。
  - 理由 · 规范建议本机只绑定回环地址；服务暴露到预期以外的网络时，任何人都能尝试调用写工具。
- **MUST** `PRO-19` HTTP 请求带 `Authorization: Bearer`，密钥至少是 24 字节随机数，恒定时间比较，失败只回 401，同一来源连续失败后限流；健康检查端点（如果有）只返回版本等非敏感信息。服务端的密钥存在受保护的用户存储中，不进命令行参数和日志；客户端配置里的明文密钥写入威胁模型（没有威胁模型时写入 README），作为剩余风险。
  - 理由 · 能写入真实工程的服务不能被同网段的其他机器直接调用。
- **MUST** `PRO-20` [规范] stdio 的 stdout 只输出协议，日志写 stderr 或文件。
  - 理由 · stdout 混入日志会破坏协议通信。
- **MUST** `PRO-21` [规范] 限制工具调用频率：对目标的调用按 [`ENG-05`](04-engineering-adapters.md#eng-isolation) 串行，排队有上限；此外服务设调用频率上限，超过时返回 `retryable: true` 的工具错误。
  - 理由 · 模型可能在循环中反复调用耗时工具，让工程师无法工作。
