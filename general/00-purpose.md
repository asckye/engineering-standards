# <a id="purpose"></a>0 目的、等级与读法

> **要点** 按项目等级只采用需要的规则：S 级只要最小清单、黄金路径和任务手册。冲突时安全与契约优先；例外写 ADR。

## <a id="purpose-parts"></a>0.1 组成

| 部分 | 文件夹 | 何时采用 |
|---|---|---|
| 通用规范 | [general/](README.md) | 全部项目 |
| MCP 服务 | [mcp/](../mcp/README.md) | 通过 MCP 向 AI 客户端提供工具（草稿）；其中[工程软件适配层](../mcp/04-engineering-adapters.md)也用于经厂商 API（COM 或 .NET）驱动另一款工程软件的工具 |
| 上位机 | [hmi/](../hmi/README.md) | 与 PLC、仪表、驱动通信，供操作员监视和操作 |
| 视觉 | [vision/](../vision/README.md) | 用工业相机做检测、测量、定位或识别（草稿） |
| 大屏 | [dashboard/](../dashboard/README.md) | 长期显示数据的大屏和看板（草稿） |
| 桌面应用 | [desktop/](../desktop/README.md) | WPF、WinUI，以及适用时的 Electron、.NET MAUI；其中本机软件、Windows、打包和诊断也用于其他在用户或现场机器上运行的软件 |
| Web 开发 | [web/](../web/README.md) | 前端、后端 API、运维 |
| 移动 App | [mobile/](../mobile/README.md) | iOS、Android 及跨平台框架 |
| 语言附录 L1–L3 | [general/languages/](README.md#languages) | 项目使用的语言 |

项目类型的规则比通用规范更具体，两者冲突时以项目类型的规则为准。但项目类型的文件不放宽别处的 MUST：引用的 MUST 仍是 MUST，只有明确写明的例外才算。

规则尽量按平台中立的方式写；写到具体平台时，说的是这个平台上的做法。语言和平台的具体做法在语言附录和 [desktop/windows.md](../desktop/windows.md)。其他平台用等效做法，不算例外，不需要 ADR。

术语：**目标**是软件最终作用的对象（目标软件或设备）；**厂商 API** 是目标软件或设备厂商的编程接口；**写入**是任何改变目标、设备、配置或用户文件的操作；**维护者**拍板范围、设计和发布。

“写入先确认”和“结果未知”的规则（`P-04`、`SEC-03`、`ERR-07`–`ERR-10`）针对自动化或 AI 发起的写入，以及对目标软件和设备的写入。用户在自己的界面中保存或删除数据按 `UI-21`、`UI-39`；Web 的幂等重试和移动的离线同步按各自的规则。

## <a id="purpose-tiers"></a>0.2 项目等级与适度原则

| 等级 | 典型项目 | 采用 |
|---|---|---|
| [S] | 小工具、脚本、内部原型。能写真实设备、真实工程或生产数据，保存或外传他人个人数据，或者对外提供服务的项目不算 S 级，至少按 M 级 | 最小必做清单是必须的；黄金路径和任务手册照做，手册步骤链接的规则按本行处理；未标等级的规则作为默认做法，用得上就用，偏离不必写理由；标 [M+]、[L] 的不适用 |
| [M] | 对外发布的产品 | 再加未标等级和标 [M+] 的规则 |
| [L] | 关键、受监管或 7×24 运行的系统 | 再加标 [L] 的规则 |

- **SHOULD** `G-01` 流程与检查随项目规模和风险伸缩：项目只采用自己等级的规则，S 级项目不为详细章节付出流程成本。等级写在项目 README 中，改变等级由维护者决定。
- **SHOULD** `G-02` 每条规则都要在质量或安全上值回成本；拿不准时选更简单的规则。
- **SHOULD NOT** `G-03` 没有具体风险时加流程：额外的评审轮次、压力重跑、审计、文档。

> **理由** 小工具照搬工厂系统的流程只会拖慢交付；工厂系统省掉流程会出事故。

## <a id="purpose-read"></a>0.3 用语与优先级

**MUST** 必须满足，例外只经 ADR；**SHOULD** 默认做法，偏离在 PR 或任务说明中写一行理由；**MAY** 允许。规则编号（如 `ERR-04`）供评审引用，规则删除后编号不复用，所以编号不连续；未标等级的规则对 M、L 有效，对 S 是默认做法（[0.2](#purpose-tiers)）。级别怎么定见 [0.7](#purpose-levels)。

冲突时依次服从：安全不变量与已发布的对外契约 > 维护者采纳的 ADR > 本规范的 MUST、SHOULD（项目类型的规则优先于通用规范）> 外部基线（各章引用的标准）> 文件既有风格（只在修改旧文件时沿用）。

质量属性的优先级（冲突时前者赢）：

| # | 属性 | 含义 |
|---|---|---|
| 1 | 在真实目标上正确 | 在真实的目标软件或设备上正确 |
| 2 | 安全 | 人员、设备、数据安全 |
| 3 | 简单 | 没有防御性膨胀和推测性抽象 |
| 4 | 一致 | 同一件事一种名称、一种写法 |
| 5 | 可诊断 | 从请求号追到日志 |
| 6 | 可测试 | 没有目标也能测 |
| 7 | 可扩展 | 只在真正会变的地方 |
| 8 | 性能 | 只在关键路径 |
| 9 | 可复用 | 只在项目内 |

## <a id="purpose-exceptions"></a>0.4 例外与 ADR

- **MUST** `G-04` 对 MUST 的例外，以及改变结构、对外契约、安全边界、发布门禁、外部基线或第三方组件的决定，写 ADR（[20.2](20-documentation.md#docs-adr)）；写明范围和到期条件。
  - 理由 · 难回退的决定有记录，避免反复争论和返工。
- **MUST** `G-05` ADR 由维护者采纳；AI 代理只能写“提议”状态的 ADR。
  - 理由 · 代理能自己采纳 ADR 时，就能自己免除任何 MUST。
- **MUST NOT** `G-06` 未经维护者批准删除、跳过、放宽任何检查、测试、断言或阈值。认为检查有误时保持原样并附证据报告。
  - 理由 · 防止用放宽检查让结果变绿，掩盖真实缺陷。

## <a id="purpose-gov"></a>0.5 规范本身的维护

- **SHOULD** `G-07` 本规范有版本号和日期（当前 2.1，2026-11-05）：删除或放宽 MUST 升主版本，新增规则或提高级别升次版本，措辞修正升修订号；每次变更记入[规范变更记录](appendix/changelog.md#changelog)。草稿（0.x）的级别还可以调整，不受此限。
- **SHOULD** `G-09` 每个项目在里程碑或发布后的回顾中复查一次：把教训写成规则，把成本高于收益的规则删除或降级。

## <a id="purpose-signals"></a>0.6 健康信号

只看四个信号，从 Git 和问题跟踪中取数，不建度量体系；只用来决定收紧或删除哪些规则，不用来评价个人。

| 信号 | 怎么看 | 偏高时考虑 |
|---|---|---|
| 交付周期 | 任务开始到合并的中位数 | 任务说明是否不清、改动是否过大、流程是否过重 |
| 返工轮次 | 每个任务退回实现者的次数 | 诊断是否不足、任务说明缺验收标准或预先批准的断言 |
| 合并门时长 | 每次合并门的耗时（目标约 15–20 分钟） | 检查选择是否过宽、是否有可复用的结果 |
| 发布后缺陷 | 发布后发现的缺陷数，按 S1–S3 | 哪类测试或实机核对缺失 |

## <a id="purpose-levels"></a>0.7 级别怎么定

本规范是标准，项目遵守它。级别按违反规则的后果定，不看现有项目做到了多少。

**MUST** 用于违反后就可能直接造成下面任一后果的规则：

- 数据或工程被写坏、丢失，或者无法恢复、无法追查；
- 写入绕过人的确认；
- 凭据或个人数据泄露，恶意代码到达用户，或者违反法律和许可证；
- 人员或设备受到危险；
- 软件崩溃、挂起或停机，而且没有人发现或恢复不了；
- 用户或模型按错误的结果行动，而且看不出来；
- 已发布的对外契约失效；
- 工程底线失守：检查失去作用，回归进入主干，或者留下要跨多处才能清除的结构问题（如复制的逻辑、散落各层的外部依赖）。这一项只用于评审时能明确判断是否违反的规则。

**SHOULD** 用于其余规则。**MAY** 用于可选的能力。

另一条 MUST 已经完全挡住时，不另定规则：引用它，或者为了文件自成一体原样重述，级别相同。一条规则只有部分内容符合，或者全部做到的成本高于收益（`G-02`）时，拆开，只把符合的部分定为 MUST。项目类型的文件可以把这些后果写得更具体，也可以增加本领域特有的后果。

- **SHOULD** `G-12` 新增规则或改变级别时按这个标准判断，不按现有项目做到了多少；每条 MUST 写一行理由，说明违反后出什么问题。
