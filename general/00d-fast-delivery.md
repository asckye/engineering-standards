# <a id="fast"></a>★ 快速交付

> **要点** 快的前提是反馈快、一次做对、不试错。拖慢反馈回路的检查必须说明它防住了什么。

## <a id="fast-loops"></a>反馈回路目标

| 回路 | 内容 | 目标 |
|---|---|---|
| 内循环 | 增量构建 + 改动涉及的测试 | 1–2 分钟 |
| 合并门 | 只跑受影响的检查 | 约 15–20 分钟；项目可设更严格的目标 |
| 夜间检查 [M+] | 冷启动的完整检查 | 45 分钟以内；失败阻止发布 |
| 发布 | 核对证据、打包、上传 | 几分钟 |

- **SHOULD** `FAST-01` 拖慢某个回路的检查写明它防住的缺陷或风险；说不出就移到夜间检查，或经维护者批准删除。
- **SHOULD** `FAST-02` 慢测试（单个超过约 5 秒或需要真实资源）单独标记，只在合并门的受影响范围或夜间检查中运行。
- **SHOULD** `FAST-03` 一台机器同时只跑一个重型门禁（用机器级锁）；并行的任务排队合并，不同时跑两套完整检查。

## <a id="fast-ai"></a>AI 优先交付

- **MUST** `FAST-04` 一到两轮完成：主导代理先诊断，再按 T.4 写说明（验收标准、修改前失败的测试、预先批准的断言变化、标准约束）；不把“去调查一下”交给实现代理。
  - 理由 · 说明不清是返工轮次最多的原因。
- **SHOULD** `FAST-06` 沙箱与主机分工：实现代理在沙箱中跑构建、相关测试和快速合并门，列出跑不了的项；主导代理在第一轮后立即在主机上跑这些项（网络夹具、并行构建、界面、实机）。
- **SHOULD** `FAST-07` 只为真正的决定停下来问人：范围、对外契约、放宽检查、安全或设备安全边界、新运行时依赖、发布。其余按推荐方案继续，并在报告中说明。

| 最费时间的做法 | 改为 |
|---|---|
| 失败后反复重跑，期待变绿 | 先定位原因，再带具体问题退回 |
| 额外的“加固”轮次和防御层 | 只修阻塞合并或发布的问题（P-18） |
| 没有决定等着它的实验 | 先写出“结果会改变哪个决定”，否则不做 |
| 最后才发现要改断言或基线 | 在任务说明中预先列出并获批 |
| 测试等真实时间 | 注入时钟（TST-05） |
| 只在合并时才跑主机检查 | 第一轮后立即跑（FAST-06） |
