# <a id="playbooks"></a>★ 任务手册

> **要点** 日常工作按手册走，不必先读章节。每一步链接到规则，遇到问题再查。

## <a id="play-new"></a>新建项目

1. 定等级（S/M/L）和项目类型，读对应文件夹的规范，写进 README（[T.1](appendix/t-templates.md#tpl-readme)）。
2. 按黄金路径建骨架、构建入口、锁文件、分析器和格式化配置（[★ 黄金路径](00b-golden-path.md#golden)）。
3. 建合并门命令和 CI，让第一条测试在两分钟内跑完（[★ 快速交付](00d-fast-delivery.md#fast)）。
4. 写代理说明（[T.8](appendix/t-templates.md#tpl-agents)），复制术语表（[附录](appendix/glossary.md#glossary)）；[M+] 写明允许用的 AI 服务（AI-19）。
5. [M+] 写 ADR 0001“采用本规范”、`SECURITY.md`、`THIRD-PARTY-NOTICES`；开启多因素认证（SEC-43）；面向欧盟用户时写 CRA 的 ADR（SEC-44）。
6. 用“新增功能”手册做第一个功能。

## <a id="play-feature"></a>新增功能

1. 写需求与验收标准（[18.2](18-process-review-git.md#review-req)）；[M+] 涉及个人数据时更新数据清单（DAT-08）。
2. L2 且 [M+]：一页设计说明，维护者批准（[T.3](appendix/t-templates.md#tpl-rfc)）。
3. 拆成可独立合并的任务，每个写任务说明（[T.4](appendix/t-templates.md#tpl-task)）。
4. 先把验收标准写成测试，再实现；只在边界校验（P-21）。
5. 内循环：构建 + 相关测试，两分钟内反馈。
6. 提交 PR（[T.5](appendix/t-templates.md#tpl-pr)）；评审（[18.5](18-process-review-git.md#review-code)）；合并门。
7. CHANGELOG、文档、实机核对清单同步（[第 23 节](23-definition-of-done.md#dod)）。

## <a id="play-bug"></a>修复缺陷

1. 登记（[T.6](appendix/t-templates.md#tpl-bug)），按 S1–S3 分级；S1 先用配置停用相关功能（[13.1](13-defects.md#bugs-triage)）。
2. 归类：真实缺陷、不稳定测试、环境、本分支回归（BUG-03）。
3. 复现并定位根因；不试错（BUG-04）。
4. 写一个修复前失败的测试（BUG-02）。
5. 最小修复，内循环通过，评审与合并门。
6. [M+] S1 写复盘（BUG-06）。

## <a id="play-refactor"></a>重构

1. 写明“行为不变”的范围和目的（可读性、去重复、为某个功能铺路）。
2. 先补对等测试，锁住现有行为（Q-17）。
3. 单独成批，不混入行为变化；新旧路径并存（Q-18）。
4. 小步合并，每步过合并门；对等测试通过后删除旧路径。

## <a id="play-dep"></a>增加依赖

1. 先确认标准库或已有依赖做不到。
2. 核对包名和发布者（DEP-01）、许可证（DEP-02）、维护状况、体积与传递依赖。
3. 精确锁定版本并入锁文件（DEP-03）；离线还原可用（DEP-04）。
4. 更新 `THIRD-PARTY-NOTICES`（DEP-06）；[M+] 更新 SBOM（DEP-11）。
5. [M+] 运行时依赖经维护者批准，写一行理由或 ADR。

## <a id="play-release"></a>发布

1. 维护者确认版本号和范围；发布期间不改代码（BLD-07）。
2. 核对发布证据：[M+] 最近一次夜间检查通过且之后无失败。
3. 生成发布说明和“未验证”清单（[T.7](appendix/t-templates.md#tpl-release)），核对支持矩阵；[M+] 测过从上一版本升级（TST-13），不能直接退回时写明恢复办法（BLD-12）。
4. 由发布命令改版本号、打包、算 SHA-256；[M+] 生成 SBOM。
5. 预发布标为预发布、不设为最新；附测试清单与反馈模板（PKG-08）；[M+] 能控制范围时分阶段发布（BLD-11）。
6. 上传后更新交接文档与发布记录；[M+] 按写明的方式观察（BLD-11）。

## <a id="play-deliver"></a>上线交付 [M+]

1. 确认验收标准和验收人（ACC-01）。
2. 准备交付内容，在干净的机器上走一遍（ACC-04、ACC-05）。
3. 关掉调试入口，移交账号、密钥、证书和许可证（ACC-06、ACC-07）。
4. 培训；运行手册和运行责任、监控告警、备份恢复、会到期的东西到位（ACC-10、OPS-01–03、OPS-05、OPS-12、OPS-13、OPS-17）。
5. 验收并记录（ACC-02，[模板](../templates/acceptance-record.md)）；上位机和视觉按[上位机规范 B.13](../hmi/README.md#pb-acceptance)。
6. 替换在用系统时写切换方案，备份，演练回退（ACC-08）。
7. 切换，观察（ACC-09）；更新交付台账（ACC-11）。

## <a id="play-hotfix"></a>热修复

1. S1 先用配置停用受影响的功能，告知用户。
2. 在主干上按“修复缺陷”手册修复，带回归测试。
3. 合并门加受影响的实机核对；发布修订版本（`X.Y.Z+1`）。
4. 发布说明写清影响范围和升级要求；复盘。

## <a id="play-incident"></a>处理事故 [M+]

1. 确认影响范围，按 S1–S3 分级（[13.1](13-defects.md#bugs-triage)）；S1 指定一人负责，开始记时间线（OPS-08）。
2. 先止损（OPS-07）：可能影响人员或设备安全时，先让设备进入安全状态；其余情况停用功能、重启、回退或切换到备用。这些操作由人执行（OPS-24）。写入结果未知时停下，不重放（ERR-08、ERR-10）。
3. 影响用户的数据、安全或结果正确性时，主动通知（OPS-09）。
4. 恢复后定位根因（BUG-04），按“修复缺陷”手册修复。
5. S1 写复盘，把教训变成检查项、测试或告警（BUG-06、OPS-10）。

## <a id="play-retire"></a>退役产品 [M+]

1. 维护者决定并写 ADR，按支持政策定停止日期（EOL-01）。
2. 提前通知用户：停止日期、替代方案、升级路径和数据迁移方法（EOL-05）。
3. 通知期内保证用户能导出或读出自己的数据（EOL-07）。
4. 到期后标明版本状态（EOL-06）。
5. 确认还在运行的版本不依赖要关闭的服务，再按清单收尾，这些操作由人执行（EOL-08、OPS-24）；保住域名和包名（EOL-09）。
6. 归档仓库和资料（EOL-10）。

## <a id="play-onboard"></a>新成员或新代理入门

1. 读最小必做清单、黄金路径和本手册（约 15 分钟）。
2. 读项目的代理说明、交接文档和术语表；代理在隔离的环境里运行（AI-20），真实凭据和客户数据不发给外部模型（AI-18）。
3. 本机跑一次构建和合并门，确认环境可用。
4. 代理：只接收按 T.4 写的任务说明，遵守 [19.4](19-ai.md#ai-machine) 的开发机规则。
5. 第一个任务选 L1（小修复或补测试），走完整的评审与合并。
