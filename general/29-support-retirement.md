# <a id="eol"></a>29 支持期与退役

> **要点** 用户要知道哪个版本还有人修、修到什么时候。停止支持要提前说，用户的数据要带得走，留下的密钥和域名要收回来。

本节适用于对外发布或交给别人运行的项目。步骤见[退役产品手册](00c-playbooks.md#play-retire)。

## <a id="eol-policy"></a>29.1 支持政策

- **MUST** `EOL-01` [M+] 写明支持政策：哪些版本还在支持，修什么（安全问题、严重缺陷、功能），支持到什么时候。写在 README；发布说明写本版的支持状态并链接到它。
  - 理由 · 没有写明时，用户不知道什么时候必须升级，供方也说不清要维护多少个旧版本。
- **SHOULD** `EOL-02` [M+] 每个版本的支持状态有一张表：支持中、只修安全问题、已停止。这里是本产品的版本；目标软件版本按 `MIG-06`。
- **SHOULD** `EOL-03` [M+] 现场长期运行的软件，支持期按设备寿命评估；写明依赖的操作系统、运行库和 SDK 各支持到什么时候，到期前给出升级或隔离方案。
- **MUST** `EOL-04` [M+] 支持政策承诺修复的版本，在支持期内能重建出来：保留工具链版本、依赖快照和构建说明（`BLD-04`、`DEP-04`），每个版本进入只修复状态时验证一次。厂商 SDK 不入仓库（`DEP-07`），副本由项目私下保管。
  - 理由 · 承诺了修复却构建不出来，就等于没有支持。

## <a id="eol-notice"></a>29.2 停止支持

- **MUST** `EOL-05` [M+] 停止支持前提前通知，通知期写在支持政策中：停止日期、替代方案、升级路径和数据迁移方法；没有替代方案时写明没有。写进发布说明，并在软件内或下载页能看到；已知的客户直接通知。
  - 理由 · 没有提前通知，用户来不及迁移，只能继续用没人修的版本。
- **SHOULD** `EOL-06` [M+] 已停止支持的版本在下载页和 README 标明状态，不再作为默认下载。标明状态不改已发布的资产和标签，不算改写（`BLD-07`）。

## <a id="eol-retire"></a>29.3 退役

- **MUST** `EOL-07` [M+] 数据由我们保管的产品，退役前用户能把数据导出带走：格式公开或有文档，通知期内导出功能一直可用。数据只在用户机器上时不需要导出功能：写明数据位置和格式，并保证用户不因授权到期或服务关闭而读不出自己的数据。
  - 理由 · 产品关闭后，用户的数据就拿不回来了。
- **MUST** `EOL-08` [M+] 退役时按清单收尾：先确认还在运行的版本不依赖要关闭的服务（授权、激活、更新检查、模型或配方下载），依赖时先给出离线授权或替代办法。撤销服务端证书、密钥、令牌和服务账号；代码签名证书除非私钥泄露不撤销，让它自然到期并销毁私钥。关闭端点和定时任务；按保留要求删除或归档用户数据和备份，并留下记录。没有服务端的产品只处理自己持有的凭据和更新通道（`EOL-09`）。这些操作由人执行（`OPS-24`）。
  - 理由 · 关掉授权服务会让现场的系统停下来；撤销签名证书会让已安装的软件不被信任；没人管的密钥和端点会变成攻击入口。
- **MUST** `EOL-09` [M+] 退役后不释放域名、包名和更新通道的所有权，除非确认已经没有旧版本在访问它们，或者更新和安装都校验独立于它们的签名，接管后也推送不了。更新通道先给出最后一条说明，再关闭。
  - 理由 · 被别人接管后，可以向还在运行的旧版本推送恶意更新。
- **SHOULD** `EOL-10` [M+] 仓库和资料归档：仓库设为只读，README 写明状态、最后版本和替代方案；`SECURITY.md` 写明已退役，发现高危漏洞时只发布公告；源码和构建资料按合同或许可证要求保留。

## <a id="eol-support"></a>29.4 用户支持

- **SHOULD** `SUP-01` [M+] 写明用户怎么报告问题：渠道、要附什么（版本、诊断编号）、响应目标；没有承诺时写“尽力而为”，安全问题按 `SEC-34`。已知问题列出受影响的版本、绕过办法和修复版本，公开发布的公开列出，交付的告知接收方；未修复的安全漏洞修复后才公开。
